Chapter 01

Workload & capacity fundamentals

Before designing GPU infrastructure, translate “100k concurrent users” into requests, tokens, memory pressure and user-visible latency objectives.

1.1 Concurrency means different things

Connected sessions are users with an open web or app experience. They may be reading or idle. In-flight generation requests are requests queued, prefilling or decoding. Running sequences are those actively using model execution and GPU KV state. These counts are not interchangeable.

1.2 Little’s Law gives us request throughput

In stable systems, the average number of in-flight requests L is the product of request arrival rate λ and mean time in the system W.

L = λ × W   →   λ = 5,000 / 20 = 250 requests/s

At 500 output tokens and 1,000 input tokens per request:

Output: 250 × 500 = 125,000 tok/s
Input: 250 × 1,000 = 250,000 tok/s

Prompt and output tokens do not cost the same GPU time. Prefill processes many positions together; decode generates tokens sequentially for each sequence.

A model must fit in GPU memory, and its replicas must produce enough tokens while meeting latency targets. These are different constraints.

Raw BF16 weight memory is approximately 70 billion × 2 bytes = 140 GB. FP8/INT8 raw storage is about 70 GB, and INT4 about 35 GB. Real quantized deployments also need scales, metadata and implementation-specific overhead.

A single 141 GB H200 cannot comfortably host 140 GB of weights plus useful KV and runtime headroom. We need model sharding or quantization.

2.3 KV cache math

2.4 GPU replicas and data parallelism

A tensor-parallel group divides a single model across GPUs; a data-parallel replica is another independent model copy that handles different requests. More independent replicas improve aggregate request throughput, but fewer GPUs per model group can increase individual-request latency or KV pressure.

2.5 A benchmark-first sizing equation

Assume a hypothetical eight-H200 replica sustains 2.5 requests/s and 50 concurrent generations within our latency SLOs. At a planned operating fraction of 70%, take the larger of the replica counts demanded by request throughput and active streams.

Replicas = ceil(max(250 / (2.5 × 0.7), 5,000 / (50 × 0.7))) = 143

At eight GPUs/replica, this is 1,144 H200 GPUs in the illustrative non-zone-failover baseline. These throughput figures were not measured; the resulting count is conditional, not a procurement estimate.

Evenly spreading 143 replicas across three availability zones does not protect against losing one third of them: the two surviving zones would provide only around 237.5–240 req/s of hypothetical maximum capacity, below the required 250 req/s.

2.7 How to measure real capacity

Use a representative mix of prompt sizes, response sizes and arrival patterns. Search for the highest SLA-compliant goodput, not simply the maximum tokens/sec with unbounded latency. Measure GPU memory, KV pressure, preemptions, p95/p99 TTFT and TPOT, queueing, and the number of completed requests. Benchmark TP=2, TP=4 and TP=8 independently.

Chapter 03

Inside the inference engine

Once a request reaches a model replica, a transformer executes prefill and decode. The inference scheduler decides which sequences use the GPU at each iteration; the KV cache prevents redundant recomputation.

3.1 One token through a transformer

The model receives integer token IDs from a tokenizer, maps them to embeddings, processes them through 80 decoder-only transformer layers, projects the final hidden state into logits, and samples a next token. A decoder block includes normalization, causal self-attention, feed-forward transformations and residual connections.

Attention(Q,K,V) = softmax((Q Kᵀ / √dₖ) + causal mask) V

Queries (Q) represent which information the current token seeks; keys (K) identify matching information; values (V) carry the information being aggregated. During decoding, the model reads old K/V tensors for earlier positions and computes new representations for the latest token.

Prefill

TTFT includes queueing, prefill and first-token delivery. TPOT measures the pace of subsequent token generation. Prefill is often compute-bound, while low-batch decode is often sensitive to model-weight and KV memory bandwidth; those characterizations change with batch size and context length.

3.3 KV caching in action

Without caching, each decode step could recompute projections for all earlier token positions. Instead, each layer stores previously calculated key/value tensors. When a new token is processed, its key and value are appended, while past cache entries are reused. Attention still has to read relevant cached state; KV caching doesn't eliminate attention work.

3.4 Continuous batching: replace slots without waiting for everyone

In static batching, a group of requests may run together until the longest one finishes. Requests that finish early leave unused slots, and new arrivals wait. Continuous batching revisits the active set after each execution iteration and admits new requests as slots and token budgets permit.

Use the comparison below. User C arrives after the first two iterations. Under a fixed batch, C waits longer. Under continuous batching, C can begin while A is still decoding.

3.5 PagedAttention: logical blocks mapped to non-contiguous physical blocks

A naive KV allocator may pre-reserve contiguous space for a maximum possible sequence or frequently reallocate as the sequence grows. PagedAttention separates the logical order of a sequence from the physical GPU-memory blocks that store it. A block table maps logical block 0 to physical block 7, logical block 1 to physical block 2, and so on.

Blocks can be allocated as needed and released when a request finishes. Only the tail block is usually partly filled in a simple paged representation. Prefix cache sharing can let eligible requests reuse blocks, subject to security and lifetime rules.

3.6 Chunked prefill protects decode responsiveness

Suppose a new request arrives with 20,000 input tokens while other users are receiving streamed responses. A monolithic prefill may delay already-running decode work. With chunked prefill, the scheduler can split that prompt and interleave its chunks with decode work under a per-iteration token budget.

For a budget of 2,048 scheduled positions, if 100 active decode sequences each need a token, the scheduler has up to 1,948 positions remaining for prefill, subject to local KV capacity and fairness.

3.7 Putting the scheduling loop together

PYTHON · Scheduler pseudocode
# Educational pseudocode: not vLLM's source implementation.
while serving:
    token_budget = MAX_BATCHED_TOKENS
    scheduled = []

    # Keep existing streams responsive.
    for req in running_requests:
        if req.needs_decode and token_budget >= 1:
            if kv_cache.can_reserve(req, 1):
                scheduled.append((req, 1))
                token_budget -= 1

    # Admit new requests and continue partial prefills.
    for req in waiting_requests:
        chunk = min(req.remaining_prompt, token_budget,
                    MAX_PREFILL_CHUNK)
        if chunk > 0 and kv_cache.can_reserve(req, chunk):
            scheduled.append((req, chunk))
            token_budget -= chunk

    if not scheduled:
        continue

    results = model.forward(scheduled)
    for result in results:
        apply_result_to_request(result)
        send_output_if_available(result)
        if result.finished:
            kv_cache.release(result.request)

A production scheduler must additionally handle cancellation, fair multi-tenant queues, preemption, KV-cache fragmentation and refcounts, speculative decoding, sampling constraints, CUDA graph capture, prioritization and state consistency.

Design decision 03Use a mature, benchmarked inference engine with continuous batching, paged KV allocation, bounded admission and chunked prefill. Optimize SLA-compliant goodput, not GPU occupancy alone.

Chapter 04

Distributed serving architecture

How does a model replica receive a request, know where its output goes, and stream it back without routing every token through the admission controller?

4.1 Separate the control plane from the streaming data plane

Our application has an edge/load-balancer layer, horizontally replicated API gateways, admission and routing services, and a large GPU worker pool. The critical design is that routing decisions can use a separate control path from token streaming.

There is another valid implementation: Gateway → Admission → Router → Worker can be a literal chain of streaming reverse proxies. But then every proxy handles every response chunk and may become another source of latency and failure. For our large deployment, we prefer to keep admission and routing off the token path.

4.2 How does the GPU replica know which gateway receives tokens?

It doesn't have to discover the gateway at all. The gateway selects the worker and initiates an HTTP request over an established connection. The GPU worker writes incremental bytes to the response of that same request. The gateway reads the bytes and forwards them to the originating client.

  1. Client submits a generation request to Gateway G1.
  2. G1 asks the admission/router tier to authorize and place the request.
  3. Router selects healthy Replica R42 and obtains a short-lived worker reservation.
  4. G1 opens POST http://r42.internal/generate with that reservation.
  5. R42 executes prefill/decode and streams SSE over its existing HTTP response.
  6. G1 relays SSE chunks to the original client over the client↔gateway stream.
  7. Completion or cancellation releases local KV resources and reservations.

The replica might simultaneously serve connections from many gateway instances. Every request has its own HTTP response stream, so data is delivered to the correct caller without an application-level reverse routing lookup.

4.3 Anatomy of the two connections

4.4 Inference-aware routing

A standard round-robin load balancer cannot distinguish a 200-token prompt from a 16,000-token prompt. A model router should consider running sequences, queue depth, KV-cache pressure, recent processing rates, health, and eligible reusable prefixes.

A practical first policy is Power of Two Choices: sample two healthy workers, then choose the one with a smaller predicted load. More advanced policies may add prefix-cache reuse, balancing lower prefill cost against expected queue delay.

4.5 Admission control and bounded queues

Routing selects where to run a request. Admission control decides whether accepting it is safe. A robust hierarchy includes per-user concurrency limits, per-tenant token and request budgets, per-request maximum lengths, global sustainable token capacity, and worker-level KV limits.

If the fleet has no capacity, place the request in a short bounded queue only if it can plausibly start and meet the remaining TTFT deadline. Otherwise reject promptly. An unbounded queue hides overload, grows waiting time and wastes resources on requests that have already timed out.

4.6 SSE: server-sent output chunks

Server-Sent Events (SSE) is a one-way event format over a streaming HTTP response. Each event is delimited by a blank line. If the client uses POST, browser code commonly reads the streaming response using fetch(); the browser's native EventSource API makes GET requests.

HTTP · Illustrative SSE stream (custom schema)
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

event: delta
data: {"text":"Tensor"}

event: delta
data: {"text":" parallelism"}

event: done
data: {"finish_reason":"stop"}

The worker streams a response to the gateway. The gateway forwards events to the client, typically without parsing their semantic content. In HTTP/1.1, streaming can use chunked transfer encoding; HTTP/2 uses DATA frames. A model token, an SSE event, an HTTP chunk and a TCP packet are not guaranteed to correspond one-to-one.

PYTHON · Minimal FastAPI worker
import asyncio, json
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.post("/generate")
async def generate(payload: dict):
    async def events():

            await asyncio.sleep(0.2)  # stand-in for inference
            yield "data: " + json.dumps({"delta": token}) + "\n\n"
        yield "data: [DONE]\n\n"

    return StreamingResponse(events(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache"})

import httpx
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.post("/chat")

Chapter 05

Distributed GPU execution

A GPU replica may itself span several devices. Split operations across tensors, pipeline stages and independent replicas; then account for synchronization, memory topology and KV-state transfers.

5.1 Three complementary forms of parallelism

StrategyWhat's divided?Main benefitMain cost
Data parallelism (DP)Independent request streams among copies of the modelMore independent schedulers / request throughputReplicated model weights
Tensor parallelism (TP)Matrix operations inside a layerSmaller weight shards and concurrent layer computeFrequent GPU collectives
Pipeline parallelism (PP)Consecutive transformer layersModel-depth partitioning; neighbor transfersSequential traversal and pipeline bubbles
GPU count = TP × PP × DPFor this simplified 3-dimensional topology; other parallelism types are possible.

Eight GPUs could be arranged as TP=8/PP=1/DP=1, as two TP=4 replicas (DP=2), or as a single TP=4/PP=2 pipeline. The best topology is workload-dependent.

5.2 Tensor parallelism from matrix algebra

A transformer linear layer computes Y = XW. With column-wise tensor sharding over four GPUs, write the weight matrix as W = [W₀ W₁ W₂ W₃]. GPU i computes Yᵢ = XWᵢ. Its output is a shard of Y.

For a following row-parallel projection, GPUs compute partial contributions Zᵢ = HᵢW₂,ᵢ, then combine them:

Z = Σ Zᵢ   (across the TP group)

5.3 Collective GPU operations

ALL-REDUCE
[2,3,5,7] → [17,17,17,17]
Sum partial tensors and give the result to all ranks.
ALL-GATHER
[A] [B] [C] [D] → [ABCD] × 4
Collect shards into a full tensor on each rank.
REDUCE-SCATTER
Reduce + shard
Sum partials, distribute only portions of the result.
POINT-TO-POINT
GPU A → GPU B
Send an activation to a neighboring pipeline stage.

Libraries such as NVIDIA NCCL implement GPU collectives. In common tensor-parallel transformer layouts, there may be roughly two synchronized reductions per layer. For 80 layers, that's about 160 collective steps per forward pass, though exact counts differ by model and engine implementation.

Tstep ≈ Tcompute + Tcommunication + Tstragglers

For a ring-based all-reduce with p GPUs, n bytes per rank, startup latency α and effective bandwidth B, a classic approximation is:

Tall-reduce ≈ 2(p − 1)α + [2(p − 1) / p] × n/BAlgorithm-specific model: NVSwitch topologies can use other collective strategies.

Collectives are synchronization-sensitive. If three GPUs finish a compute phase quickly and a fourth is delayed, other GPUs may wait for the straggler before the collective completes. More GPUs can mean more communication rounds or complex topology effects.

5.5 Pipeline parallelism by layer groups

Instead of splitting each layer's matrices, give different consecutive layers to different GPUs or GPU groups. For a four-stage 80-layer model, stage 1 owns layers 1–20, stage 2 owns 21–40, stage 3 owns 41–60, and stage 4 owns 61–80.

With only one microbatch, pipeline stages often wait for one another. Multiple independent microbatches can keep different stages busy at once. But for an individual autoregressive sequence, the next generated token still depends on the previous one completing, so the simplified forward-only pipeline visualization is only an approximation.

Different placements on a single eight-H200 node expose different trade-offs:

For BF16 Llama 70B on H200, a useful first experiment is TP=4 with two replicas per node. But compare against TP=2 and TP=8 on the same node-level traffic distribution and SLA. The goal is highest goodput/GPU, not fastest single-request benchmark.

5.7 Disaggregated prefill/decode

Collocated workers do both prompt processing and token generation. An alternative is to run prefill workers and decode workers as separate pools. Prefill computes prompt KV tensors; a KV-transfer channel moves that state to a decode worker; the decode worker continues generation and streams output back to the gateway.

The admission/router tier now must select compatible prefill and decode workers. The gateway can establish an output stream with the decode worker and separately submit the prompt to prefill. The KV transfer occurs between the GPU services. Transfer connectors, request IDs, model versions and cache layouts must agree across both sides.

5.8 The cost of moving KV state

KV transfer ≈ prompt tokens × 327,680 bytes

For our 1,000-token average prompt: 327.68 MB of BF16 KV per request. At 250 requests/s this is 81.92 GB/s aggregate KV transfer across the fleet, if the entire prompt cache is transferred once per request with no reuse, compression or partial pre-placement.

5.9 Will disaggregation make inference faster?

Not automatically. It can isolate latency-sensitive decode from compute-heavy prefill, and the two pools can use different schedules and GPU topologies. But KV handoff introduces network traffic and coordination overhead. Benchmark for a real improvement in TTFT/TPOT goodput, not an assumed automatic throughput gain.

Arrival capacity ≤ min(Cprefill / input tokens, Cdecode / output tokens, BKV / KV bytes/request)Decode also needs sufficient concurrent-sequence and KV-cache capacity.

Our current target workload needs 250k prompt tokens/s, 125k output tokens/s and 5k active decode sequences. A disaggregated design must provision all three processing constraints and enough KV transfer capacity. As prompt length grows, the transfer fabric can become its own bottleneck.

5.10 A sensible build-and-benchmark sequence

  1. Begin collocated. One eight-H200 server, with a TP=4/DP=2 candidate; compare TP=2 and TP=8 independently.
  2. Benchmark mixed prompts. Include short, long and bursty traffic; record goodput, TTFT, TPOT, KV use, and collective latency.
  3. Try PP only if warranted. Measure stage occupancy and point-to-point transfers.
  4. Diagnose interference. Determine whether long prefill causes unacceptable decode jitter even with chunking.
  5. Only then test P/D separation. Include KV-transfer latency, fabric utilization and failure handling in the comparison.
Design decision 05Start with a simple collocated TP/DP serving configuration, quantify network and collective costs, and change topology only when measurements prove it improves SLA-compliant goodput or reliability. Recalculate total GPU fleet requirements after selecting the winning topology.

6.2 Why cold GPU starts defeat simple reactive scaling

A GPU worker does not become useful the moment a scheduler raises its replica count. Capacity may need to be provisioned, container images fetched, model weights loaded into memory, distributed ranks initialized, kernels warmed, and readiness verified.

We will use an illustrative 180-second cold-start time in the experiments. Actual p95/p99 time-to-ready must come from infrastructure measurements; quota shortages can delay or prevent GPU provisioning entirely.

6.3 Separate the three control loops

FAST LOOP

Admission control

Milliseconds to seconds. Decide accept, briefly queue, reject, or cancel based on ready capacity and deadlines. Protect the current cluster immediately.

REACTIVE LOOP

Replica requests

Seconds to minutes. Use queue age, offered demand, token load and KV pressure to request more capacity; account for replicas already provisioning.

PREDICTIVE LOOP

Prewarm capacity

Minutes to hours. Estimate demand at least one cold-start lead time ahead, prewarm workers, and preserve fault reserve.

Ndesired ≈ max ( ⌈λ̂ / (u μr)⌉, ⌈λ̂ Î / (u μi)⌉, ⌈λ̂ Ô / (u μo)⌉, ⌈Ĉ / (u μc)⌉ )λ̂=forecast requests/s; Î, Ô=mean tokens/request; Ĉ=active generations; μ terms are compatible, measured per-replica capacities; u=utilization ceiling. Also impose KV memory constraints.

Do not derive the μ terms from unrelated best-case microbenchmarks. In production, capacity is a multidimensional feasible operating region for prompt, decode and concurrency mixes.

6.5 Queue-driven autoscaling and backpressure

Use both offered load (including otherwise-eligible capacity rejections) and queue work. If 500 short requests are waiting and our target is to clear them in 10 seconds while admitting 250 RPS, the controller sees a rough demand of 300 RPS:

λrequired ≈ λincoming + Q / Tdrain = 250 + 500/10 = 300 RPS

For heterogeneous workloads, estimate queued token work, not only request count. Queueing cannot repair a 180-second provisioning delay for a two-second TTFT objective, so the fast admission loop should reject excess work before an unbounded backlog forms. A 429 typically indicates quota exhaustion; a 503 can indicate regional inference capacity exhaustion.

Don't allow multiple autoscalers to fight.Use one authoritative desired-replica controller per model/region serving pool. The HPA, node autoscaler and custom forecasting components should have clearly separated responsibilities.

6.8 Autoscaler controller pseudocode

The controller must distinguish ready, warming and provisioning replicas. Only ready capacity protects the live traffic SLO, while pending capacity counts toward avoiding duplicate provisioning requests.

Python · desired capacity by failure domain
from math import ceil

def desired_per_zone(forecast, measured, utilization=0.70):
    # Per-replica capacities come from compatible workload tests.
    n = max(
        ceil(forecast.rps / (utilization * measured.rps)),
        ceil(forecast.input_tps / (utilization * measured.input_tps)),
        ceil(forecast.output_tps / (utilization * measured.output_tps)),
        ceil(forecast.active / (utilization * measured.active_limit)),
        measured.kv_replica_minimum(forecast),
    )
    # Three zones; must survive any single zone failure.
    return ceil(n / 2)

def reconcile(zone, target_per_zone, state):
    ready = state.ready(zone)
    pending = state.warming(zone) + state.provisioning(zone)
    if ready + pending < target_per_zone:
        request_replicas(zone, target_per_zone - ready - pending)
    elif ready > target_per_zone and scale_down_is_stable(zone):
        drain_workers(zone, ready - target_per_zone)
    # Never route toward warming/provisioning/draining workers.
    publish_ready_worker_registry(zone)

Reliability & observability

A serving cluster may return HTTP 200 while generated text stalls or ends abruptly. Reliability must be defined at the completed generation boundary and traced across gateways, admission, and inference workers.

7.1 Define what a successful generation means

HTTP status alone is insufficient for streaming inference. A worker might write a few tokens, then crash. The status code remains 200, but the response did not finish. Our primary availability SLI classifies each eligible logical generation only after successful completion, timeout, or definite interruption.

Generation success = eligible request + valid stream + successful terminal completionCount an otherwise-eligible 503 for regional capacity shortage as a service failure. Normally exclude intentional client cancellation and invalid/quota-ineligible requests, but audit the exclusions.

7.2 Error budgets and burn rate

At 250 eligible requests/sec continuously, a 30-day window contains 648 million requests. With a 99.9% availability SLO, the allowed bad-request fraction is 0.1%, or 648,000 bad requests.

Budget30d = 250 × 86,400 × 30 × (1 − 0.999) = 648,000A full service outage equivalent of 43.2 minutes in a 30-day steady-demand window.

Error-budget burn rate compares current failure fraction to the allowed 0.1% failure fraction. If 1% of eligible requests fail, we burn at 10× our sustainable budget rate.

7.7 Cancellation and reservation cleanup

When the user clicks Stop or disconnects, the gateway cancels its upstream worker HTTP stream. The GPU engine removes that sequence from future scheduler iterations, frees its KV blocks, and releases capacity permits. Already-submitted GPU work may finish before the cancel takes effect.

Our proposed cancellation cleanup objective is p99 ≤ 2 seconds after cancellation reaches the serving backend. A lease/TTL prevents gateway crashes from leaving permanent reservations behind. The worker must be safe under repeated or late cancellation messages.

7.8 Healthy versus routable workers

Probe/stateMeaningOperational rule
StartupModel loading and initialization finished?Don't restart during legitimate long startup.
LivenessIs the process fundamentally broken?Do not restart merely because GPU is busy or queue is full.
ReadinessShould the router assign new work?Only after model and engine pass serving checks.
DrainingShould worker finish existing requests but reject new placements?Remove from admission while keeping process alive.

When a worker crashes, the router immediately stops new placements after failure detection. Existing streams on that worker usually lose volatile KV state and terminate; a different worker can regenerate, but should not silently continue after partial output unless a deliberate replay/checkpoint protocol exists.

Chapter 08

Benchmarking & production cost

A GPU count isn't credible until it comes from measured SLO-compliant capacity, representative arrival patterns, and failure-aware placement. Our goal is the lowest total cost per good request, not the largest raw tokens/sec number.

8.1 Throughput, capacity and goodput are different

Raw throughput measures how much the server completes when pushed hard. SLO-safe capacity is the highest sustainable offered rate at which our client latency, queue stability and reliability gates pass. Goodput counts individual requests that actually complete successfully under those bounds.

Goodput (req/s) = ( Σ 1[successi ∧ TTFTi ≤ 2 s ∧ TPOTi ≤ 80 ms] ) / T

A system can meet p95 TTFT and p95 TPOT separately without having 95% of requests satisfy both simultaneously. Request-level goodput captures their joint constraint. Track SLO compliance and stable queues in addition to goodput.

8.2 Use two benchmarking environments

A. Full-node comparison

One isolated eight-H200 node, controlled model/engine setup, and an external load generator. For TP=2 or TP=4, run multiple independent model replicas on disjoint GPU groups and benchmark their combined node-level throughput.

B. End-to-end platform

Distributed generators → gateway → admission + routing decision → selected GPU replica. Include client-visible SSE, cancellation, queue deadlines, overload and failure injection.
